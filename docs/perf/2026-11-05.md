# Launcher benchmark, 2026-11-05

Same TV as 2026-11-04 (Mi TV Stick, Android 11, 2 GB, `DeviceTier` MID), same debloated
system state for every run — only the launcher differed. Method: cold boot, 60 s idle
settle, system `/proc/meminfo` + launcher `dumpsys meminfo`, then a cold start and the
same fixed 12-key DPAD walk at 0.45 s for `gfxinfo`. Raw dumps in `2026-11-05/`.

Sonora run: `app-perf.apk` built from `performance-optimization` @ `2c6e17a`.
Google TV runs: `com.google.android.tvlauncher` 7.7.15 re-enabled for the test
(`tvrecommendations` was already enabled; `backdrop`/`mitv.dream` were enabled for run
parity, then disabled again — they only serve the screensaver, which is off).

## Reading

- **Memory:** Sonora holds ~40 MB PSS; Google TV's launcher holds ~180 MB at idle and
  grows to ~275–288 MB after navigation — roughly 6–7x Sonora, and ~95 MB more of the
  device's RAM unavailable. This matches the 2026-10-31 record (~286–298 MB).
- **Frames:** Sonora misses ~2.7% of deadlines vs ~6–8% for Google TV, with p99 less
  than half (48 ms vs 105–200 ms) and 1 vs 13 slow-UI-thread events on the same walk.
- **Three-way, vs the pre-debloat record** (`tv-debloat/README.md`, Oct 31, stock
  everything): MemAvailable was ~688 MB with the stock launcher at ~298 MB PSS and
  ~250 MB swap in use. Today the debloated system with Google TV home shows ~803–823 MB
  available and ~41 MB swap — the debloat itself is worth ~115–135 MB. Sonora on top of
  that reaches ~897 MB.

## Caveats

- One clean Sonora run; two clean Google TV runs (they agreed within ~10%). A second
  Sonora run was attempted twice and discarded: see below.
- Google TV's process hosts more than pixels (recommendations row, channel logos,
  content providers), so its PSS includes work Sonora never does. That is the honest
  cost of the stock experience, ads included.
- The walk is identical key events, not identical UI paths — Google TV's grid differs,
  so frame counts differ. Rates and percentiles are the comparable figures.

## Operational finding: `tvlauncher` re-enables itself on boot

After `pm enable` + `set-home-activity` were used once for the Google TV runs,
`pm disable-user com.google.android.tvlauncher` stopped surviving reboot: twice, the
package came back `enabled=1` during boot and HOME opened it despite the preferred
activity and HOME role still pointing at Sonora. `backdrop`/`dream` were not the cause
(a run with them disabled reproduced it). With no further reboots the disable holds
and HOME lands on Sonora. Likely suspects not yet isolated: `tvrecommendations`,
`katniss`, or a persisted state `set-home-activity` left behind. The Oct 31 debloat may
never have survived a reboot — worth re-checking after the next one.

## Post-rewrite Sonora runs (same day, later)

Same protocol, same TV, build `master` @ `2af7e57` — i.e. including the
focus-glass slab (`22776c7`/`fc7e555`) and the `ScreensaverView` rewrite (`c4bfde4`).
`app-perf.apk` rebuilt and reinstalled; `cmd package compile -m speed` re-run. Two
clean runs; raw dumps `sonora-post-run{1,2}.*`.

| | MemAvailable (idle) | Swap used | Launcher TOTAL PSS idle | After walk | Frames | Deadline missed | 50th | 95th | 99th | Slow UI thread |
|---|---|---|---|---|---|---|---|---|---|---|
| Sonora pre-rewrite | ~897 MiB | ~41 MB | 41.4 MB | 38.1 MB | 331 | 9 (2.7%) | 7 ms | 24 ms | 48 ms | 1 |
| Sonora post run 1 | ~944 MiB | ~11 MB | 43.9 MB | 41.4 MB | 452 | 4 (0.9%) | 6 ms | 21 ms | 28 ms | 0 |
| Sonora post run 2 | — | — | — | 37.6 MB | 455 | 4 (0.9%) | 6 ms | 17 ms | 18 ms | 0 |

Reading: deadline misses dropped ~2.7% → ~0.9% and p99 48 ms → 18–28 ms; zero slow
UI-thread events both runs. MemAvailable is ~47 MiB higher at idle and swap use fell
to ~11 MB, though run-to-run boot variance is real — treat the memory delta as
suggestive, not proven. Idle PSS is ~2.5 MB higher (the focus-glass slab's layer is
the likely cost); it is still ~40 MB total.

Caveat: this walk exercises the home grid and focus path only. The screensaver
rewrite removes per-frame canvas draws by construction, but no framesaver timing was
captured — that would need a separate idle-on-dream measurement.

## Frame-phase breakdown and the dream check (same day, later still)

`dumpsys gfxinfo framestats` after the same walk (`sonora-post-run3.framestats.txt`,
120-frame ring): p50 intended-vsync→completed 8.0 ms, p90 19.2 ms, p99 35.5 ms.
Median phase costs are tiny — measure/layout/draw-record ~0.1–0.5 ms, command issue
~3.2 ms to swap. Only 4/120 frames swapped after the deadline; `FrameCompleted`
lands late on ~22% of frames because GPU completion trails swap by ~14.8 ms
median. **The remaining frame cost is GPU fill/composition, not CPU draw** — the
text-layout/StaticLayout cheap win would not move these numbers; an overdraw audit
is the only CPU-side lever left worth checking.

Dream check: the device dozed on its own 300 s timer and the system dream ran —
which also exposed that `settings secure screensaver_components` still pointed at
the dead `com.mitun.aerial` package, so the dream had never been reachable since
the rename. Set to `com.mitun.sonora/.dream.SonoraDreamService`; dream started
immediately on the next idle. 902 frames in 30 s (~30 fps, the designed 33 ms
cadence), **0 janky, 0 deadline misses, p50/p99 5 ms CPU, GPU p99 10 ms**
(`sonora-dream.gfxinfo.txt`). The `c4bfde4` screensaver rewrite is verified
cheap on-device.

## Focus-glass rim removal A/B (same day, evening)

`FocusGlassView` dropped the focus rim — tvOS lifts the focused card with a
shadow only, no outline — and retuned the three shadow layers (PAD 8→16 dp,
spread 1.5/3.5/5.5 dp, drop 2/5.5/9 dp, so nothing leaks above the card).
Measured with the newly ported `scripts/bench.py` (same 12-key walk,
`--label sonora-phaseN`): phase0 = the committed with-rim build, phase1 =
the rim removal.

| | Frames | Deadline missed | p50 | p95 | p99 | Slow UI | Idle PSS | Post PSS |
|---|---|---|---|---|---|---|---|---|
| phase0 (with rim) | 456 | 3 (0.7%) | 6 ms | 19 ms | 22 ms | 0 | 29.5 MB | bad dump |
| phase1 (no rim) | 452 | 4 (0.9%) | 6 ms | 20 ms | 34 ms | 1 | 37.5 MB | bad dump |
| phase1b (no rim) | 456 | 4 (0.9%) | 6 ms | 19 ms | 23 ms | 0 | 37.3 MB | 35.8 MB |
| phase0b (with rim) | 453 | 4 (0.9%) | 6 ms | 16 ms | 31 ms | 0 | 37.2 MB | 37.5 MB |

Frames at parity across both builds (~0.9% deadline misses, p99 22–34 ms —
the two tails, phase1's 34 and phase0b's 31, are single-run noise, not a
split between builds). Frame-neutral, as expected — the change removes one
stroke draw on a cached hardware layer.

The PSS question also closed: phase0b reran the rim build at the same
measurement point (seconds after install) and read 37.2 MB idle / 37.5 MB
post — the same as the no-rim runs. The ~8 MB gap against phase0's 29.5 MB
was app age (phase0 measured a process settled for hours), not the change.

Caveat: the first bench.py cut dumped `/proc/meminfo` for
`meminfo-app-post`, so the `sonora-phase0`/`sonora-phase1` `-app-post`
files hold system memory, not app PSS. Fixed the same day; phase1b's and
phase0b's post dumps are correct.

Verified on-device by screencap: the focused card lifts with a soft shadow
below it and no outline; the rest-state hairline on unfocused cards is
unchanged.
